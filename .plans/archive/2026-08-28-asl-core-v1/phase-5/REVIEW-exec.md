# Phase 5 Plan — executability & gates review

**Lens:** executability and gates (does each item fail loudly when wrong, and does the acceptance battery reproduce the project's real gate battery).

**Verdict:** reject

## Findings

### Blockers

**B1 — `oracle.py` is invoked by two gates but never specified.** I5's gate shells `.venv/bin/python .plans/phase-5/oracle.py $f` and I6's gate shells the same with `--root`. The contract (input → expected stdout), the writer (I0? a later item? the orchestrator?), and the very existence of the file are all unstated. §2.1 ("New files") does not list `oracle.py`; §2.2 ("Modified files") does not list it; I0 records "BASELINE.md (+ optional ORACLES.md)" but says nothing about `oracle.py`. Verified by reading §3 I5 and §3 I6 verbatim and confirming `.plans/phase-5/` contains only `PLAN.md` (`ls .plans/phase-5/` → just `PLAN.md`). Without the script, two gates are not runnable. **What makes it right:** add `oracle.py` to §2.1, name the author (I0 makes sense — it derives per-fixture expected stdout by executing the Python lowering, same data the lock requires), and document its CLI: positional fixture name, optional `--root`, stdout emission of the expected program output. Until then the I5 and I6 gates are aspirational, not executable.

**B2 — I3 gate command is structurally wrong: it runs the corpus fixture as a program, but only 5 of 29 valid fixtures declare `main`.** §2.4 CLI contract says "File without a `main`: exit 0, no output (mirrors `to_python.py host_entry`)." Verified: `grep "^defun.*main" grammar/corpus/valid/*.agentscript` finds `main` in only `13-module-program`, `14-sequenced-bodies`, `15-shadowed-binders` (`backend/differential.py` `program_cases()` lists exactly those three files — lines 373-…). The I3 gate runs `$B grammar/corpus/valid/$f.agentscript` for `01-basics,03-strings,04-longest-run,05-constructors,07-lambda-elision`, none of which declare `main`, so per the contract each produces stdout="" and exit=0. The `diff -u <(...oracle.py $f) /tmp/out.$$` therefore compares the oracle's *expected stdout* against empty stdout for every fixture. The gate will either pass trivially (oracle outputs "") or fail spuriously; either way it does not verify the interpreter. **What makes it right:** wrap each `; run:`-header expression in a generated `main` driver (the plan text mentions this in passing — "their exported entries wrapped in a generated `main` driver checked into `.plans/phase-5/`, never the corpus" — but the gate command itself runs the corpus file directly). The driver must be a checked-in artifact, not implicit.

**B3 — I6's six fixture entries include five with no `main` and one (`15-shadowed-binders`) whose `--root` argument is misrouted.** I6 gate iterates `06-module,09-imported-types,10-imported-generic-types,11-name-coexistence,12-transitive-use,15-shadowed-binders` with `$R --root grammar/corpus/modules`. Verified `; run:` headers exist for `06-module`, `09-imported-types`, `10-imported-generic-types`, `11-name-coexistence`, `12-transitive-use` (each starts with `; run:`). None declares `main` in the root module. The interpreter will exit 0 with no stdout per §2.4, the same defect as B2. Additionally, `15-shadowed-binders.agentscript` imports `core/shadow` (`grammar/corpus/valid/15-shadowed-binders.agentscript:10` shows the `:export [main string-from-shadow]` clause but the import path is whatever the source declares — verified the file lives under `corpus/valid/` and imports `core/shadow`, so `--root grammar/corpus/modules` is needed but the SOURCE argument is `corpus/valid/15-shadowed-binders.agentscript`; that resolution path is correct in principle but I6's gate omits any generator wrapping and so still hits the no-`main` problem for 5/6. **What makes it right:** I6 must generate a `main` driver (or use the same wrapper I3 should have) for every fixture, since none of the non-`13/14/15` module fixtures declare `main`. Otherwise the I6 gate cannot pass.

**B4 — The acceptance battery §4 is missing one of the seven project gates.** The project gate list in `AGENTS.md` ("Gates — both must pass before any commit") names seven commands:
1. `grammar/validate.py` — present in §4
2. `grammar/closure_audit.py` — present
3. `prelude/generate.py --check` — present
4. `checker/gate.py` — present
5. `backend/check_corpus.py` — present
6. `backend/monomorphism.py` — present
7. `backend/differential.py` — present
8. `backend/exec_coverage.py` — present
9. `pytest backend/t bench/algo checker/t -q` — present

§4 includes all of them and adds three of its own (cargo test, grep for "interp" in differential output, two `git diff` blankness guards). So §4 is *superset*, not subset. The reverse complaint holds: the `git diff` blankness checks reference `<I0 baseline>` — a placeholder; no concrete baseline commit/tag is recorded in I0's gate (`test -s .plans/phase-5/BASELINE.md && test -s .plans/phase-5/ORACLES.md`). The acceptance runs `git diff <I0 baseline>` where `<I0 baseline>` is not a defined ref. **What makes it right:** I0 records the literal SHA (e.g., `00ccb12`) into BASELINE.md, and §4 reads it from there.

**B5 — I0's "every count" claim is stated but never gated; a regressed baseline passes.** I0 says "record the per-fixture oracle outputs" and the gate `test -s BASELINE.md && test -s ORACLES.md` only checks the files exist, not that the recorded counts are correct. A reviewer who runs the gate after I0 has mis-counted (e.g., validate counts 97 `ok` instead of 98, differential finds 1 disagreement) will see the gate green. The plan's other items inherit the bad baseline. **What makes it right:** the I0 gate must compare against literal values, e.g. `grep -q 'validate 98 ok' BASELINE.md && grep -q 'differential.*0 disagreement.*120 function.*15 program' BASELINE.md && grep -q 'pytest.*161' BASELINE.md`. The existence test is the weakest possible oracle.

### Majors

**M1 — `exec_coverage.py` invariance is asserted, not enforced.** The plan says I8 leaves `exec_coverage.py` untouched and the §4 acceptance runs it as a project gate. But the plan never asserts I8 leaves `program_cases()` byte-equal: it only promises the *content* won't change. A reviewer reading `exec_coverage.py:219` (`for src, cases in differential.program_cases():`) sees the dependency is structural, not content-based — if I8 reorders cases, the tracer still runs. The two `git diff` blankness guards in §4 are the right idea but they require a defined baseline (see B4). When defined, the guard against `prelude/coverage.lock backend/cases` mutation is also unstated: the plan's I8 list of changes is to `differential.py` only, but the diff guard against `backend/cases` looks precautionary rather than tied to any I8 step. **What makes it right:** the diff guards should be enumerated as I8 sub-items, not bolted on at acceptance.

**M2 — Cargo gate at acceptance depends on I1's tree-sitter ABI pin being already correct.** §5 risk 1 names this: the pin is verified in I1 but the acceptance `cargo test` runs after I8. If the pin chosen in I1 turns out to be wrong (e.g., later ABI revision), the I1 scaffold gate passes (it builds the empty skeleton) but `cargo test` at acceptance fails on the interpreter crate whose tests use `parser.c`'s ABI. The mitigation is implicit — pin in I1, never revisit — but no test in I1 exercises the runtime path. **What makes it right:** I1's scaffold gate should also run a one-line cargo test exercising parsing end-to-end, not just compile.

**M3 — I7's gate text is non-executable.** §3 I7 says "replay every case of `08-io` and `19-io-errors` exactly as declared in `differential.py program_cases()`" but provides no command. The `differential.py` `program_cases()` lists `08-io` with 5 cases and `19-io-errors` with 7 cases (`backend/differential.py:373-…`). The interpreter arm is not in the differential runner yet (I8 is later), so I7's gate cannot simply run `differential.py`. **What makes it right:** I7 must include a literal command replaying each case via the interpreter binary with seeded `files`, `stdin`, `argv`, and asserted `stdout`/`stderr`/`exit`, matching the structure of `programs()` but locally to the interpreter.

**M4 — I2's heredoc gate does not pin string escapes.** §5 risk 11 says "I2's heredoc gate pins `\n` and `\\` unescaping explicitly." Verified: the I2 gate contains `printf ... "x\\ny"` and asserts `printf -- '-1.5\nx\ny'`. The escape is in the *expected output*, not in the *source*: the source uses `\\n` which the printf-built file would render as a literal backslash-n, not as a newline. The fixture would actually fail because the source literal isn't an escape but two characters. **What makes it right:** use a heredoc (`cat > ... <<'EOF'`) with literal escape characters, or escape the escapes one level deeper; the current heredoc writes `\\n` to the file, which the parser sees as two characters and which `println` emits as `\\n`, not a newline.

**M5 — I5's oracle.py invocation may be ambiguous about the four-fixture file scope.** I5 invokes `$B grammar/corpus/valid/$f.agentscript` for the listed fixtures. Several of those (e.g., `20-option-result-ctors`, `24-list-reshaping`, `29-literals`) have `; run:` headers and *no `main`*, so per §2.4 the interpreter produces no stdout. Same shape as B2/B3. **What makes it right:** I5 must wrap the fixtures in a generated `main` driver like I3/I6, or those fixtures stay unit-tested only.

### Minors

**m1 — `git diff` guards in §4 assume `<I0 baseline>` is a commit ref, not a tree hash.** `git diff` against a tree works but won't include uncommitted intermediate changes between I0 and I8. I0 captures the SHA into BASELINE.md; the acceptance step should `git rev-parse HEAD~N` rather than rely on a tag.

**m2 — I1's `printf ... && $B ...; test $? -eq 0` chain conflates interpreter success and shell success.** If `$B` exits 2 (parse error), the chain correctly evaluates; but if `$B` produces output and exits 0, the next test `$B /tmp/p5-bad.agentscript; test $? -eq 2` will run on the same shell state — fine here, but the heredoc leaves no `main` so per §2.4 the OK case should also exit 0 silently. The OK gate is a no-op assertion.

**m3 — Plan's Invariants table cites `differential.py:361-363` for the agreement expression.** Verified: line 361 is `agree = seen["python"] == seen["rust"] == seen["wasm"]` (a three-way tuple equality). The invariant "compares stdout+stderr+exit across ALL arms AND against the declared value" is partially supported: the agreement is among python/rust/wasm, and the *declared value* comparison happens via `declared_ok = seen["python"] == want` (line 362). After I8 the equality becomes `seen["python"] == seen["rust"] == seen["wasm"] == seen["interp"]`, which is sound. But "AND against the declared value" is checked separately (`declared_ok`); the invariant row elides that nuance.

**m4 — I0 oracle derivation: `; run:` headers compare against return values, not stdout.** The plan derives "per-fixture expected stdout for the single-module non-program fixtures by executing their Python lowering." But `; run:` headers are checked by `check_corpus.execute` (per `backend/check_corpus.py:88`) which evaluates the lowered expression and compares to the asserted literal — it is not stdout. For the interpreter, the only way to get expected stdout is to invent a `main` wrapper. The oracle's job is not "stdout from `; run:`" but "stdout from a generated program that exercises the same definitions." This is the right framing, but the plan is silent on it.

## "Conformant-but-wrong" — what passes every gate yet is still wrong

**C1 — Trivial oracle.py that echoes "$fixture_name\n" for every input.** Every I5/I6 fixture's expected stdout becomes the literal fixture name with a newline. With the interpreter emitting "" for non-`main` fixtures (per §2.4 and verified B2/B3), the diff fails — but if the implementation also cheats by emitting the fixture name verbatim, both arms agree and the gate goes green. Two implementations sharing a defect is exactly the failure shape the plan's preamble warns against ("a gate comparing two implementations that share a defect is blind"). The only witness is a checked-in oracle written by a process that does NOT itself run through the interpreter.

**C2 — Interpreter that exits 0 silently for every fixture.** Because §2.4 allows no-`main` files to exit 0 with no output, and because the corpus module fixtures (06, 09-12) and the single-module vocabulary fixtures (16, 17, 20-29) all lack `main`, an interpreter that simply does nothing for those files will: (a) pass the I3/I5/I6 `diff -u <(oracle) out` gates trivially if oracle outputs empty; (b) pass the I2 heredoc gates (those are the only fixtures with `main`); (c) fail the acceptance §4 differential.py gate only if `program_cases()` is extended to cover more fixtures — which the plan does not do. The acceptance tests interpreter on the same five files the existing differential runs (`08-io,13-module-program,14-sequenced-bodies,15-shadowed-binders,19-io-errors` — three of which need `--root`). None of the corpus's 24 `; run:`-only fixtures are exercised end-to-end under the interpreter at acceptance; the I3/I5/I6 gates are the only path, and they collapse to "no-op iff oracle outputs nothing."

**C3 — Module lowering keyed by import alias.** §5 risk 8 names this. `13-module-program` exercises one module through two aliases. If the interpreter keys global identity on the alias, that case fails in `differential.py` — but only when the interpreter is wired in (I8). Until then, an interpreter keyed on aliases passes I6's gate if oracle.py happens to derive oracles from the Python lowering (which itself keys on alias via `module_prefix`). The two agree, the gate is green, the defect ships.

**C4 — `try` returning from the lambda frame instead of the enclosing defun.** §5 risk 9 names this. I2's heredoc gate contains no `try`-inside-lambda case. The corpus fixture that exercises it would be one of the `; run:`-only ones. With oracle.py mirroring the Python behavior (which returns from the lambda frame too — verified `runtime.py` `try` raises), the interpreter and oracle would both be wrong, agree, and pass.

**C5 — Float `fmt_f64` ported with the wrong exponent padding.** The plan says "≥2 exponent digits" but the existing `fmt_f64` (referenced `rt.rs`) was tested only against the cases in `backend/cases/`. An interpreter whose `fmt_f64` produces `1e3` instead of `1e+03` for, say, `1e16`, passes the existing cases (they don't pin exponent width) and fails only if the corpus has a fixture that does. Verified: corpus fixture `29-literals` is the one cited, but it has no `main` (B2's trap).

## Risks (unverified)

- **R1 — Phase 5 may not actually be deferred to function mode entirely.** §5 risk 10 is filed as "decision for the orchestrator." The acceptance battery does not cover function mode under the interpreter; if a reviewer expects Phase 5 to also gate function mode (matching the 120 function cases), they will find a gap. The plan is explicit about program-mode-only acceptance, but the risk that "0 disagreements across 120 function + 15 program" stops reading as a full-pass at Phase 5 deserves a callout.
- **R2 — I0 baseline counts claim "validate 98 ok; checker gate 79 ok; check_corpus 31; differential 0 disagreement(s) across 120 function + 15 program cases (python/rust/wasm); pytest 161."** These were not independently re-run by this reviewer against the live tree (the plan says HEAD is `00ccb12` and the tree is clean — re-running the full battery was not in scope). The counts are claims.
- **R3 — I0's gate command uses `test -s` (existence check).** The stronger gate suggested in B5 was not verified as already present somewhere; if the orchestrator's review loop runs the weaker gate, a stale baseline passes silently.
- **R4 — The `15-shadowed-binders` fixture's import paths were not fully traced.** I verified it imports `core/shadow`; the exact `--root` requirement was not re-derived from first principles. Plan says `--root grammar/corpus/modules`, which appears consistent with `corpus/modules/` containing `core/`.
- **R5 — `prelude.json` builtin count is 107 per plan §3 I5.** I confirmed `"builtins": [` opens the array and counted `^   "` occurrences as 806 (irrelevant number — likely many leading-whitespace entries); the actual builtin count was not parsed. Cross-check with `vocab.builtins()` in `prelude/vocab.py` would be needed.
- **R6 — `29-literals` oracle is not pre-existing.** Verified §3 I5 names it, but no per-fixture oracle file is in `backend/cases/` for it (those files are function-mode JSON, not program oracles). Whether I0 derives a program-mode oracle for `29-literals` (which has no `main`) is unclear from the plan.
